# Milestone 2 security review — ops-dash

**Reviewed 2026-09-19** against `a26430c` plus the G-remediation in flight
(`server/src/api/routes.ts`, `index.ts`, `poller/schedule.ts` were being edited
while I read them; line numbers in those three files may have moved by a few
lines, the findings have not). Node v24.21.0, npm 11.19.0.

This is a review of *this* application's surface. It is the companion to
`2026-09-18-m1-review.md` and **carries that review's "Reopens at release" list
forward** — the combined list is at the end of this file and supersedes M1's.

## What changed in the threat model, stated first

M1's entire attack surface was a browser rendering fixtures. Three things now
exist that did not:

1. **The app makes outbound calls.** Five vendor status feeds and three
   reachability probes, every 60 seconds, forever. We are now a client of
   systems we do not own, and the bytes they return are input.
2. **It stores what they say.** `node:sqlite`, one file, no retention.
3. **It runs unattended.** `poller/schedule.ts` on timers. This is the first
   thing in the repo that does anything when nobody is watching, and the first
   thing whose failure mode is "quietly stops" rather than "looks wrong on
   screen".

The adversary this milestone introduces is not a reader of the dashboard. It is
**the upstream** — a vendor status page that is compromised, hijacked at DNS, or
simply misbehaving. That adversary exists today, on John's laptop, regardless of
whether the app is ever deployed. Findings H-1, H-2 and M-3 below are *not*
gated on the local-only premise; everything gated on it is marked and repeated
in the Reopens list.

Still true, and the premise the rest rests on: **ops-dash runs on John's local
machine only.** Not served to any network, not on the corp VLAN. **No credential
is read anywhere in M1 or M2** — verified by grep over `server/src`: no
`process.env`, no `Authorization` header, no secret-shaped key. Every endpoint
we touch is public and unauthenticated. M3's adapters (statusio, msgraph) are
the ones that change that, and several findings below are cheap now and
expensive after they land.

## Findings

**No BLOCKER.** Nothing in M2 is a live compromise of this machine as it stands.
That is a statement about the premise, not a clean bill of health: H-1 and H-2
are one deployment or one vendor compromise away from being the top of this
list, and both are small fixes today.

### HIGH-1 — a hostile feed body has no size limit and can OOM the process

`server/src/http/fetchJson.ts:47` — `const body = await response.text();`

The whole response is buffered into a string, then into `JSON.parse`, with no
`content-length` check, no byte cap and no streaming. `probe.ts` is exempt — it
cancels the body at `probe.ts:121`, which is correct and was verified.

**Verified, not reasoned.** I pointed `fetchJson` at a local server that streamed
a 300 MB JSON string:

```
B body bytes: 314572800   rss MB before/after: 70 → 1356   ms 1027
```

One 300 MB response cost 1.29 GB of RSS and one second. Two concurrent feeds
doing it, or one 2 GB response, kills the process. The 10 s timeout does not
save us: the timeout is on the *request*, and a fast server can deliver
gigabytes inside it — the run above moved 300 MB in 1.0 s on loopback.

**The failure scenario.** Any of the five status hosts (or anything that can
answer for their names on this machine's resolver) serves a large body once. The
poller process dies. **Nothing restarts it**: there is no supervisor, no
`unhandledRejection` handler, and the dashboard's last state stays on screen
looking exactly like a healthy one. A monitoring tool that dies silently is
worse than no monitoring tool — that is this product's own thesis applied to
itself.

**Fix.** Read the body as a stream with a hard cap (5 MB is ~50× the largest real
payload; Zendesk's `incidents.json` fixture is the biggest thing we fetch),
abort past the cap, and return a fifth failure code — `body_too_large` — as a
`SourceResult` error like every other failure here. Check `content-length` first
as a cheap reject, but do not trust it as the only check; a chunked response has
none.

### HIGH-2 — `redirect: 'follow'` means the https floor applies only to the first hop

`server/src/http/fetchJson.ts:40` and `server/src/adapters/synthetic/probe.ts:113`
set `redirect: 'follow'`. The SSRF floor is
`server/src/adapters/vendorstatus/common.ts:147` —
`!url.startsWith('https://')` — and it validates **the URL we typed**, never the
URL we ended up at.

**Verified, not reasoned.** I stood up two local servers and pointed `fetchJson`
at the first, which answered `302 Location: http://127.0.0.1:<port>/latest/meta-data/`:

```
A redirect: {"data":{"secret":"internal-service-payload","path":"/latest/meta-data/"},
             "fetchedAt":"...","degraded":false}
```

The redirect was followed, the scheme was downgraded from the caller's to plain
http, an internal address was fetched, and its body came back as a clean,
un-degraded `SourceResult` — indistinguishable from a good vendor read. The
path in that test is the EC2/IMDS shape on purpose.

**The failure scenario, honestly scoped.** Today: whoever controls
`status.helpjuice.com` (or any of the four others) can make this process issue
one arbitrary GET per minute to anything reachable from John's laptop, including
`127.0.0.1` and the LAN, and can read the answer back out of the SQLite file —
though not out of any network-reachable place, because nothing listens. That is
a real capability and a small one. **At release** — on the audit dashboard
server, on the corp VLAN — it is textbook SSRF against internal HTTP services
with the response body retrievable through `/api/services`. The status quo is
"we are one deployment away from a full SSRF primitive, and the code will not
change on that day".

**Fix.** `redirect: 'manual'`, an explicit follow loop with a small hop cap, and
the same validation re-applied to every `Location` — https only, and (see LOW-3)
not a literal IP or loopback/link-local/RFC1918 host. The cheap 80% version, if
the loop is too much for now: keep `follow`, then reject after the fact with
`new URL(response.url).protocol !== 'https:'` and drop the body. That closes the
scheme downgrade but not the https→https-to-internal case.

### HIGH-3 — the `fetchJson` exemption is file-scoped, and the file is licensed by a comment

`web/src/guards.test.ts` (the `EXEMPT_MARKER` line in *the server talks to the
network only through its one helper*): the guard skips **the entire file** if the
string `deliberately not fetchJson` appears anywhere in it, and the check runs on
the raw text *before* comments are stripped. So a comment licenses a file.

**Verified both directions**, by mutation. I added
`server/src/adapters/__guardprobe.ts` containing a doc comment with the marker
phrase and a bare `const res = await fetch(url)`:

```
✓ src/guards.test.ts (18 tests)      ← passed with the marker present
× the global fetch is not reachable outside the helper, by call OR by alias
                                     ← failed after changing the phrase
```

A new adapter that copies probe.ts's header comment — which is the most natural
way to write an M3 adapter, since probe.ts is the file you read to learn the
convention — gets a blanket pass on all four failure rules. And the four rules
are the ones that stop an expired credential's HTML sign-in page from being
reported as a successful poll of zero records, which has happened on this tenant.

**Yes, a tighter form exists, and it is nearly free.** Key the exemption to the
**line**: the marker must appear on the offending line or within the two lines
above it. I ran that rule over the whole of `server/src` as it stands:

```
OFFENDER  server/src/adapters/synthetic/probe.ts 92
          export async function runProbe(spec: ProbeSpec, fetchImpl: FetchLike = fetch)
```

**One site in the entire server.** `probe.ts:110`'s actual call is
`fetchImpl(spec.url, …)`, which is not a bare global and never trips the guard;
the only thing needing a licence is the default parameter on line 92. So the fix
is: change the guard to line-scoped, and add one marker comment above
`probe.ts:92`. The block comment stays as the argument — it just stops being the
licence. Recommend also adding a control test, in the guard's existing style, that
a marker two functions away does **not** license a bare `fetch` (the mutation I
ran above, as a permanent test).

*This is the open M2 item the lead gated on me. My answer: file-scoped is a real
hole, it is reachable by copy-paste rather than by malice, and line-scoped costs
one comment.*

### MEDIUM-1 — we poll other people's systems on a 60 s timer, anonymously, with no back-off, and nothing says that is polite

`server/src/adapters/synthetic/runner.ts:35-69` and
`server/src/index.ts:56-58` (`VENDOR_INTERVAL_MS`, `PROBE_INTERVAL_MS` = 60 s).

Per day, from one IP, forever:

| Target | Requests/day | Note |
|---|---|---|
| `support.crexendo.com/api/v2/help_center/…` | 1,440 | unauthenticated, 200 |
| `help.netsapiens.com/api/v2/help_center/…` | 1,440 | **unauthenticated, answers 401 every time by design** |
| `crexendo.helpjuice.com` | 1,440 | |
| 4 × Statuspage `summary.json` | 5,760 | |
| `status.zendesk.com/api/ssp/incidents.json` | 1,440 | |
| **Total** | **≈11,520/day** | |

**Verified:** the User-Agent we present is `user-agent: node` (observed on a
local server, for both `fetchJson` and `runProbe`). We are anonymous traffic.
And **there is no back-off anywhere**: `fetchJson` maps 429 to `http_429`
(`fetchJson.test.ts:76` asserts it), the poller records it as a failure, and the
next tick fires 60 seconds later at exactly the same rate. `Retry-After` is not
read. I grepped the repo for `rate limit`, `polite`, `backoff`, `Retry-After`
and `User-Agent`: **nothing in `server/` or the M2 plan states a polite interval
or acknowledges this at all.**

The netsapiens probe is the one to think about from the other side: 1,440
unauthenticated requests a day to an auth-required API endpoint, from an
unidentified client, each answered 401. That is the shape of credential-probing
telemetry. The likely outcome is not a security incident, it is Zendesk or
Cloudflare quietly starting to challenge or block us — which would pin the
Zendesk tile red and teach the operator that red means nothing, the exact defect
`runner.ts`'s own comment was written about.

**Recommend (not a code change I can make, and partly a decision for John):**
- 300 s for the probes and 300 s for the vendor feeds. 60 s buys nothing: every
  one of these feeds is human-updated, and the uptime figure loses resolution we
  do not present anyway.
- Per-source jitter on the first tick, so the eight calls do not arrive as a
  burst on the same second every minute.
- Exponential back-off capped at ~30 min on repeated `http_429`/`http_5xx`, and
  honour `Retry-After`. A failing source currently retries at full rate forever.
- A real User-Agent: `ops-dash/0.2 (+internal IT monitoring; john@crexendo.com)`.
  If we are going to be a persistent client of someone's API, they should be able
  to contact us rather than block us.
- Write the chosen interval and the reasoning into `vendors.json`'s `$comment`
  and `runner.ts`, so the next person does not lower it for a demo.

### MEDIUM-2 — `check_runs` grows forever; nothing prunes, nothing vacuums

`server/src/store/schema.sql:35-42`. Grepped: no `DELETE`, no `VACUUM`, no
retention anywhere in `server/src`.

**Measured, not estimated.** I inserted one year of ticks at the current cadence
(3 probes × 60 s) against the real schema:

```
rows 1,576,800   db 262.7 MB   (WAL peaked at 264 MB inside the bulk transaction)
uptime 30d 22 ms   percentiles 30d 79 ms   runsFor 1 ms
```

So: **263 MB per year and the queries stay fast.** It is not an availability bug
at M2 volume, and I will not inflate it into one. Two things make it worth a
finding anyway: it is unbounded (year five is 1.3 GB and nothing is ever
deleted), and M3 multiplies the row rate — the mailflow round trip, statusio and
msgraph all add probes and services. The time to add retention is before the
table is large, not after.

**Fix.** A daily prune from the poller: `DELETE FROM check_runs WHERE at < :90d`
(30 d is all any query asks for; 90 d leaves headroom), plus resolved incidents
older than the correlation window, plus `PRAGMA journal_size_limit` so a WAL
spike from a bulk delete does not stay resident. Add a test that the prune keeps
the newest row and removes the oldest — and watch it fail before trusting it.

### MEDIUM-3 — vendor-authored strings are stored and served with no length or content validation

`statuspage.ts:174-185` (`name` → `title`, `shortlink` → `url`),
`zendeskSsp.ts:100-113` (`attrs.name`, `attrs.postmortem` → `url`),
`statuspage.ts:165` / `zendeskSsp.ts:210` (`incidentsSince`), and the `note`
strings built in both adapters.

These go into the snapshot payload as JSON (`db.ts` `putSnapshot`), and
`/api/services` mirrors the envelope outward unchanged — which is the right rule
for the *envelope* and means nobody is validating the *content*.

Three separate consequences, in order of how much they matter:

1. **`url` is vendor-controlled and is the one field designated to become an
   `href`.** M1's review, section S4, set the rule: `VendorIncident.url` and
   `ServiceStatus.vendor.url` are the only fields that ever become an anchor, and
   `web/src/lib/safeUrl.ts` exists to parse them. I grepped: **`safeUrl` is still
   called by nothing.** Today that is inert — the web reads fixtures and the API
   is not wired to it. The day M4 wires the two together, a `javascript:`
   `shortlink` from a compromised status page is one operator click from script
   execution in the dashboard. **The server should not be shipping a URL it has
   not parsed**, regardless of what the client promises to do with it.
2. **Size.** `incidentsSince` is the vendor's *entire published incident list*,
   unbounded, re-serialised into one row on every poll. Combined with HIGH-1's
   missing cap, a feed can choose how much we write to disk every 60 seconds.
3. **Length.** Titles and notes are untruncated. React escapes them, so this is
   layout damage rather than XSS, but a 1 MB incident title is a broken page.

**Fix, in the adapters, before the store:** parse `url` with `new URL` and drop
anything that is not `https:` (drop, do not sanitise — the same argument
`safeUrl` already makes); cap `incidentsSince` at the 50 most recent; truncate
`title` to ~300 chars and `note` to ~2000.

**Verified clean on the other half of this surface:** incident *summaries* and
*titles* produced by the correlation engine contain **no vendor-authored text** —
`rules.ts:190-235` builds them from our own vocabulary, config service names and
levels. So the incident rows, which are the thing an operator reads first, are
ours end to end.

### MEDIUM-4 — the unattended process has no entry point, and that is where every release-day decision lands

**Verified:** `node server/src/index.ts` does not run.

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/server/src/store/db.js'
  imported from …/server/src/index.ts
```

The source uses `.js` specifiers with no build step, and Node 24's type-stripping
does not rewrite them. And even if it resolved, `index.ts` exports `createApp`
and never calls `schedule.start()` or `api.listen()`. `CLAUDE.md` line 19
documents `node --watch server/src/index.ts` as "run the server: store + poller +
adapters + engine + API, one process". **It has never run unattended. Nothing in
M2 has.** Every claim in this review about long-running behaviour is therefore a
claim about the code, not about observed uptime; I say so rather than implying
otherwise.

This is a plan/docs defect (the lead owns the fix), but it is in a security
review because the missing file is where four security decisions get made, and
they get made by whoever is in a hurry that day:

- **Bind address.** Fastify's `listen({ port })` defaults to localhost, but
  `host: '0.0.0.0'` is the reflex, and with `auth: { mode: 'none' }` that
  publishes an unauthenticated API to the VLAN in one line. Bind `127.0.0.1`
  **explicitly**, so the next person has to delete an intention rather than
  forget one.
- **`process.on('unhandledRejection')`** and an exit that says why. HIGH-1's OOM
  and any future escape from `tick` currently produce a silent death.
- **Timers are all `unref()`'d** (`schedule.ts:183`), so a poller-only process
  exits immediately. The listener is what holds the loop open; if the entry point
  ever starts the poller without listening, it will appear to do nothing.
- **Graceful shutdown** — `store.close()` on SIGINT/SIGTERM, or WAL files are
  left behind on every stop.

### LOW-1 — vendor-controlled text reaches `/api/health` and the log, untruncated

`fetchJson.ts:44` builds `http_<status>` errors as `${status} ${statusText}`.
**Verified:** a server answering with a 4,000-character reason phrase produced
`error.message` of length 4,004, intact. That string becomes
`SourceStatus.lastError`, which `/api/health` serves and which the in-flight
logging change writes to stderr. The only bound is undici's 16 KB header limit,
not anything of ours. Not injectable (an HTTP reason phrase cannot carry CR/LF)
and React escapes it downstream. **Fix:** truncate to ~200 chars in `err()`.

### LOW-2 — the store path is CWD-relative with default permissions

`db.ts` `openStore(path = 'ops-dash.sqlite')` — created wherever the process
started, mode by umask, with `-wal`/`-shm` beside it. `.gitignore` covers all
three, verified. Nothing sensitive is in it today (public vendor status and our
own latency numbers). Worth an explicit configured path and 0600 **before** M3,
because M3's adapters are the first that read credentials, and a store that
caches a Graph response is a different object from this one.

### LOW-3 — the SSRF floor pattern-matches instead of parsing

`common.ts:147` — `url.startsWith('https://')`. It accepts
`https://user:pass@host/…` (credentials in a config file, which is precisely the
thing `guards.test.ts` exists to keep out of this repo), and it accepts
`https://127.0.0.1`, `https://[::1]`, `https://169.254.169.254` and any RFC1918
host. Reasoned from the code; **not reproduced**, because reproducing it means
editing `vendors.json`, which I do not own.

Who can actually write that file: anyone with commit access or local write
access to the repo. There is no network path to it, no upload, no runtime
override — so this is floor quality, not a live vulnerability, and it is the
*second* line of defence behind HIGH-2 rather than the first. **Fix:** parse with
`new URL`; reject a non-empty `username`/`password`; reject literal-IP hosts and
`localhost`/`.local`. Same helper then serves the redirect check in HIGH-2.

### LOW-4 — the first runtime external dependency, and the budget it opened

`server/package.json` adds `fastify@5.12.5` — the first runtime dependency
outside React. **`npm audit --omit=dev` reports 0 vulnerabilities** (verified,
exit 0). The runtime tree is now **53 packages** where M1 had three. The lock
file is committed. No action today; the action is at release: re-run
`npm audit --omit=dev` as a release gate rather than a one-off, and decide
consciously whether a 53-package runtime tree is the deployment posture we want
behind an unauthenticated API.

## Verified clean

These were checked and found sound. Recorded because "we looked and it holds" is
worth as much as a finding, and because each is a thing a future change could
break quietly.

| Check | Result |
|---|---|
| **Prototype pollution through a parsed feed body** | **Clean.** The only merges of parsed data are object **spreads** (`{...result, data: vendor}`), which create own properties and do not invoke setters — `JSON.parse('{"__proto__":…}')` is inert through them. No `Object.assign` into a shared object, no recursive merge anywhere in `server/src` (grepped). Every vocabulary lookup is guarded by `Object.hasOwn` (`statuspage.ts:58,66`, `zendeskSsp.ts:52`), not by a bare index — so `constructor` and `__proto__` cannot select a level |
| **Deep-recursion / stack exhaustion via `JSON.parse`** | **Clean today, and fragile.** Verified: a 200,000-deep array parses on Node 24 without throwing (V8's parser is iterative); the `RangeError` appears only if something later `JSON.stringify`s it. No consumer recurses over a raw body — every adapter replaces `data` with its own flat `Vendor` before `db.ts` stringifies it, so the deep structure is discarded before it reaches the store. It stops being inert the day any code path stores or re-serialises a raw vendor body. Worth stating in M3's brief |
| **SQL injection** | **None.** Every statement in `db.ts` is `db.prepare` with `?` placeholders, prepared once at open; no string-built SQL anywhere in `server/src` |
| **Credentials** | **None read, none present.** No `process.env`, no `Authorization`, no secret-shaped key in `server/src`. `guards.test.ts` covers `server/src` for credential paths (confirmed at its `files` line). The four Python clients' paths stay in `docs/RESUME.md` and nowhere else |
| **Probe bodies** | Not downloaded — `probe.ts:121` cancels the stream after headers. So HIGH-1 does not apply to the probes, and the latency number is not polluted by body size |
| **A failed read never becomes green, below the UI** | Holds through the new layers: `fetchJson` returns errors as data, the poller treats an errored envelope as a failed poll (the G2 BLOCKER-1 fix), `signals()` refuses a stale payload's level, and `unknownVendor` is the single failure shape. This is the product's central promise and M2 did not lose it |
| **Correlation output carries no vendor text** | `rules.ts:190-235` — titles and summaries are built from our own vocabulary and config names only |
| **The API is read-only** | Every registered route is a GET, asserted over the route table, `exposeHeadRoutes: false`. `/api/health` reports `auth: { mode: 'none' }` at runtime |
| **`npm audit --omit=dev`** | 0 vulnerabilities |
| **Server test suite** | 374 tests, 24 files, typecheck clean, at the time of review |

## What I could not check

- **Nothing has ever run unattended** (MEDIUM-4). Every statement here about
  timer behaviour, memory over hours, or WAL growth in steady state is read from
  the code and from short synthetic runs, not observed over a day.
- **I did not run against the live vendor endpoints.** The traffic arithmetic in
  MEDIUM-1 is arithmetic; whether Zendesk or Cloudflare would actually throttle
  us is a prediction. The hand-run in Task 9 is the only live evidence in the
  repo, and it was 2026-09-19 one-shot, not sustained.
- **LOW-3 is reasoned, not reproduced** — it requires editing `vendors.json`,
  which I do not own.
- **The https→http downgrade in HIGH-2 was reproduced over plain http**, with a
  redirect to an internal address. I did not stand up a TLS origin to prove the
  literal `https:` → `http:` hop; that behaviour is WHATWG-fetch default and
  undici implements it, but I am flagging it as the one step in that finding I
  inferred rather than watched.
- **I did not run the full `npm test`.** Three server files were being edited by
  another agent while I reviewed. I ran the server project (374 pass) and
  `guards.test.ts` (18 pass, plus the mutation in HIGH-3).

## Reopens at release

**This is the list that matters, and it now supersedes M1's.** Every item is
struck, deferred or tolerable *today* only because ops-dash runs on one local
machine that nothing connects to. The day it is served to anything — the audit
dashboard server, a VLAN, a colleague's browser — each of these becomes live, and
**nothing in the code will announce it**. Whoever deploys this owns this list.

### Carried from Milestone 1, still open

1. **Authentication and authorization.** The seam exists (`routes.ts`,
   `auth: { mode: 'none' }`); nothing fills it. M4. Today there is no reader but
   John; at release the API is an unauthenticated read of the estate's health.
2. **`frame-ancestors`.** Ignored in a `<meta>` CSP — header only. Clickjacking
   is moot on localhost and not moot on a server.
3. **Transport security.** No HTTPS, no HSTS.
4. **The CSP must move to a header**, with `frame-ancestors` and a `report-uri`.
   Note also that the current policy's `connect-src 'self'` is what M4's wiring
   to the API has to satisfy — if the API is served from another origin, that
   line must change deliberately and not by widening to `*`.
5. **Credential handling, now at Milestone 3** (was "at M2" — M2 read none).
   statusio and msgraph are the adapters that read credentials. Their paths stay
   in `docs/RESUME.md` and never in source; `guards.test.ts` asserts it.
6. **Rate limiting and the poller's own behaviour** — now concrete, see MEDIUM-1.
   EPC allows 10 access tokens per refresh token per 10 minutes; that ceiling
   arrives with M3.
7. **Server-side injection classes** — a server now exists. SQL is parameterised
   (verified); the classes that remain open are SSRF (HIGH-2) and resource
   exhaustion (HIGH-1).
8. **The demo-mode query parameter.** `?demo=quiet|sev1` swaps the entire data
   set. Safe as written, and M4 should remove the provider.

### New at Milestone 2

9. **SSRF becomes real the moment there is an internal network.** HIGH-2. The
   follow-redirect hole is worth little on a laptop and is a full internal-GET
   primitive on a server with a metadata endpoint or a management LAN. Fix it
   before deploying, not after.
10. **The bind address.** MEDIUM-4. When the entry point is written, bind
    `127.0.0.1` explicitly. `host: '0.0.0.0'` plus `auth: { mode: 'none' }` is a
    one-line publication of the estate's health to anyone on the VLAN.
11. **`/api/services` republishes vendor-authored strings**, including
    vendor-authored URLs, to every client. MEDIUM-3. Today the only client is
    fixtures-driven and there is no client at all in practice. At wiring (M4)
    this is the path from a compromised status page to an `href` in our UI, and
    `safeUrl` is still called by nothing.
12. **`/api/health` exposes the shape of our estate** — every source name, every
    error string, our polling cadence, and (LOW-1) untruncated vendor text. That
    is a fine local diagnostic and an unauthenticated reconnaissance endpoint on
    a network. It needs auth with the rest of the API, or an allowlist.
13. **Retention.** MEDIUM-2. 263 MB/year measured at M2 cadence, unbounded, no
    prune. A deployed instance runs for years and gains M3's probes.
14. **Process supervision.** MEDIUM-4 and HIGH-1 together: no restart, no
    `unhandledRejection` handler, no graceful shutdown. A monitoring system that
    dies silently is the failure this product exists to prevent, aimed at itself.
    At release it needs a supervisor (systemd/NSSM) and an external check that
    the checker is alive.
15. **The store file.** LOW-2. Explicit path, 0600, and a decision about backup —
    it will hold the estate's health history, and from M3 possibly cached vendor
    data obtained with a credential.
16. **Outbound traffic becomes attributable to the company, not to a laptop.**
    MEDIUM-1. On the corp network, 11,520 anonymous requests a day leaving a
    server — including 1,440 that are answered 401 by design — is a thing the
    security team will eventually ask about. Give it a User-Agent and a written
    interval before they do.
17. **The runtime dependency tree is 53 packages.** LOW-4. `npm audit --omit=dev`
    becomes a release gate, not a one-off check.
