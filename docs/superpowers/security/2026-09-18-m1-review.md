# Milestone 1 security review — ops-dash

**Reviewed 2026-09-19** against the tree at Task 11A. This is a review of *this*
application's surface. A generic web checklist passes here trivially and tells you
nothing, because in Milestone 1 there is no server, no authentication, no user
input, no database and no network.

## The premise, stated first because it sets everything below

**ops-dash runs on John's local machine only** (confirmed 2026-09-19). Not served to
any network, not on the corp VLAN, not on the audit dashboard server. The spec's
"deployment target is the existing audit dashboard server" is the *eventual* target,
not a current fact.

That strikes the adversary who would otherwise dominate this review. There is no
unauthenticated reader because there is no reader but John. Nothing below is
justified by a confidentiality argument a local-only app does not have — and
everything struck on that basis is listed under **Reopens at release**, which is
the most important section of this document.

Two things are true regardless of who can read the page:

1. **From Milestone 2 the data we render is authored by strangers.** Seven upstream
   feeds and four product APIs return strings we display. A Statuspage incident
   title, a Graph advisory body, a Proofpoint mail **subject** and **sender
   address** — every one written outside this company, and in the mail case by
   someone actively hostile who chose that text on purpose. The Email page's whole
   job is to display attacker-authored content. That is the point of the page, not
   a flaw in it, but it makes the page's escaping a security control rather than a
   formatting detail. **A local-only app is still a browser**: a `javascript:` URL
   from a vendor feed executes in it just the same.
2. **The build chain runs code from a file we did not write.** `extract-icons.mjs`
   evals a 2.1 MB vendored bundle and writes the result into a module every page
   renders through `dangerouslySetInnerHTML`.

One rule survives the change of premise for a different reason. **Fixtures stay
redacted** — not because the page is exposed, but because the repo has a remote and
fixtures are committed and pushed. A real UPN in a committed fixture leaves the
machine even when the app never does.

## The five surfaces

### S1 — The single HTML sink · CLOSED

`Icon.tsx` is the only `dangerouslySetInnerHTML` in the app. It is safe only while
three properties all hold, and each is now asserted rather than assumed:

| Property | Held by |
|---|---|
| Content is generated at build time from a vendored file, never at runtime | `extract-icons.mjs`, plus the S5 pin below |
| `IconName` is a closed union, so no runtime string selects a glyph | TypeScript |
| Generated bodies are `<path>` geometry only | `guards.test.ts` — rejects `<script>`, `on*=`, `javascript:`, `xlink:href`, `<image>`, `<foreignObject>`, `url(` |
| No second sink exists | `guards.test.ts`, and the exemption for `Icon.test.tsx` is conditional on that file still containing its proof |

**A defect was found here and fixed at gate G3 (H-1).** `{...rest}` was spread
*after* `dangerouslySetInnerHTML`, and `IconProps` omitted only four props from
`SVGProps` — so `dangerouslySetInnerHTML` was a legal, typed prop on `<Icon>`.
Reproduced: `<Icon name="shield" {...hostile} />` rendered
`<image href="x" onerror="1">`. **The repository guard could not see it**, because
it greps for the literal string and a spread does not contain one. Fixed by moving
the spread above the sink and adding the prop to the `Omit`; a regression test
defeats the type-level `Omit` with a cast, on the reasoning that the `Omit`
protects typed call sites and the runtime should be safe without it.

The plan's Task 3 Step 8 still carried the unsafe ordering and was amended at
source, because regenerating `Icon.tsx` from the plan would have reintroduced it.

The plan's verification step for this surface — `grep -rn "<Icon" | grep -v 'name="'`
expecting no output — is **too crude and does not hold**. Three call sites pass a
variable: `Header.tsx` a ternary of two literals, `Sidebar.tsx` `item.icon` from the
`NAV` table, `Alert.tsx` `c.icon` from a closed record. All three are typed
`IconName` from closed sources, which is the property that matters. The check worth
running is that no *runtime* string reaches `name`, and the type system enforces it.

### S2 — Reflected route parameters · CLOSED

`/services/:id` and `/incidents/:id` take an arbitrary string from the URL and the
error copy interpolates it back into the page. React escapes text children, so this
is safe **by default** — meaning one future `dangerouslySetInnerHTML` or one
`href={id}` turns it into reflected XSS. The Playwright suite fires
`<img src=x onerror=…>` through both routes and asserts nothing executes. Keep that
test; it is the only thing standing between "safe by default" and "safe".

### S3 — Browser storage · CLOSED

`ops-dash.theme` is read on boot and drives a class name. `ThemeProvider.initial()`
compares the stored value against `'light'`/`'dark'` and falls back to `null`
otherwise, inside a `try`/`catch` — storage can throw in a partitioned context and
can return junk. Verified at `ThemeProvider.tsx:30-34`.

### S4 — Untrusted content rendered as data · RULES SET, NOT YET LIVE

Nothing renders vendor data in Milestone 1; all content is fixtures. The rules are
set now so Milestone 2 has no excuse:

- Mail **subjects** and **sender addresses** render as **text only**. Never a link,
  never a `title`, never into any HTML sink. A subject line is attacker-chosen by
  definition.
- Vendor advisory **notes** and incident **titles** render as text only.
- `VendorIncident.url` and `ServiceStatus.vendor.url` are the only fields that ever
  become an `href`, and they are vendor-supplied.

`web/src/lib/safeUrl.ts` is written and tested although nothing calls it yet.
It **parses** rather than pattern-matches, and drops anything that is not `https:`
rather than sanitising it — we have no use for a vendor link that is not https, and
"sanitise" is how these bugs come back. The test carries a control proving a naive
`startsWith('https:')` accepts a value `safeUrl` rejects.

Any anchor rendering a vendor URL also carries `target="_blank" rel="noopener
noreferrer"`; the Playwright link test enforces both across every route.

### S5 — Build-chain integrity · CLOSED

`extract-icons.mjs` now pins the bundle by SHA-256 and refuses to eval on mismatch.
Verified both ways: the committed bundle regenerates `icons.generated.ts`
byte-identically, and appending a single newline makes the build throw with the
mismatch message rather than shipping.

That matters because a swap of that file is arbitrary code at build time on this
machine *and* arbitrary markup on every page. It is vendored, committed and
diffable, which is most of the defence; the pin is the part that fails loudly.

## Hardening applied

- **Content Security Policy** in `index.html`. Its value here is not
  confidentiality — it makes the **zero-external-dependency rule enforceable by the
  browser** rather than by a grep and good intentions. The day someone re-adds a
  Google Fonts `@import` or a CDN script, the browser refuses it and a test goes
  red. Verified the app survives its own policy: inline styles apply (React uses
  CSSOM, which CSP does not govern), the vendored webfont loads as a real face,
  keyframes resolve, the focus ring renders, no console violations.
- **`web/public/app.css`** created, because `style-src 'self'` *does* govern a
  literal `<style>` block. This also gave two G1 accepted findings their permanent
  home: `@keyframes aur-skel-pulse`, without which every `Skeleton` rendered a
  static grey block, and `:focus-visible`, which no file under `web/src` could
  express. Both were invisible to the entire test suite and visible only in a
  screenshot.
- **`favicon.svg`** generated from the already-extracted brand glyph, removing the
  last 404.

## Reopens at release

**This is the list that matters.** Every item below is struck *today* only because
the app is local-only. The day it is served to anything — the audit dashboard
server, a VLAN, a colleague's browser — each becomes live, and nothing in the code
will announce it.

1. **Authentication and authorization.** The spec defers sign-in and keeps an auth
   seam in the API from day one. Today there is no reader but John; at release
   there is. The seam exists; nothing fills it.
2. **`frame-ancestors`.** Ignored in a `<meta>` CSP — it only works as an HTTP
   header. Clickjacking is moot on localhost and is not moot on a server.
3. **Transport security.** No HTTPS, no HSTS. Irrelevant to a local file server,
   required the moment it has a hostname.
4. **The CSP itself needs to move to a header**, alongside `frame-ancestors`, and
   should gain `report-uri` once there is somewhere to report to.
5. **Credential handling, at Milestone 2.** Four Python clients' credential files
   are read from disk by the adapters this milestone deliberately does not build.
   Paths are recorded in `docs/RESUME.md`; those paths are exactly what must never
   be transcribed into source, and `guards.test.ts` asserts it.
6. **Rate limiting and the poller's own behaviour.** Seven upstream feeds polled on
   timers is an outbound traffic pattern someone may notice; EPC allows 10 access
   tokens per refresh token per 10 minutes.
7. **Server-side injection classes** — none exist while there is no server.
8. **The demo-mode query parameter.** `?demo=quiet|sev1` is validated to a closed
   union and reaches no sink, so it is safe as written. But at release a URL
   parameter that swaps the entire data set is a feature nobody should be able to
   trigger by accident; Milestone 4 removes the provider entirely and should.

## One finding not fixed

`Integration['state'].error` has no fixture row, so that badge's *layout* has never
been rendered or measured — only its token pair, resolved synthetically. Not a
security finding; recorded here because it was found while checking that every
state renders, and because "a state nothing renders is a state nobody has looked
at" is a pattern this milestone hit repeatedly.
